# SIIS — Structured Interview Integrity Score

**Quality of hire has always measured the wrong person.**

Most organizations measure hiring quality by looking at the candidate — first-year performance, 12-month retention, hiring manager satisfaction. All lagging. All aimed at the wrong target. The strongest predictor of whether a hire will succeed isn't a candidate attribute. It's whether the interviewer actually ran a structured interview or just had a conversation and called it one.

Meta-analytic research has been clear on this for 30 years. [Sackett, Zhang, Berry & Lievens (2022)](https://pubmed.ncbi.nlm.nih.gov/34929079/) rank structured interviews (r = .42) as the single strongest selection method available — above cognitive ability tests, work samples, and every other method evaluated. The barrier was never knowledge. It was that adherence was nearly impossible to measure at scale.

That's what this project explores: using an LLM to score interviewer adherence to structured interviewing best practices, across ten dimensions, from transcripts and scorecards. The framework (SIIS) comes from [Zach Williams's writing](https://zjwilliams.substack.com/p/youre-measuring-the-wrong-person); this repo is my implementation of it as a working proof-of-concept.

---

## What this is

A Python package that takes an interview transcript or written scorecard and returns per-dimension pass/fail verdicts with coaching-grade rationale, plus a Streamlit app that demonstrates the end-to-end flow on synthetic data.

```python
from siis import score_interview

result = score_interview(
    interview_id="int_001",
    interviewer_id="erik_001",
    role="Senior Software Engineer",
    scorecard="Candidate seemed really sharp and had great energy. Good culture fit. Recommend hire.",
    competency_coverage="fail",      # from interview guide
    evaluation_independence="pass",  # from ATS timestamps
)

print(f"{result.dimensions_passed}/10 — tier: {result.tier}")
for v in result.llm_verdicts:
    print(f"  [{v.verdict}] {v.dimension_key}: {v.rationale}")
```

**Real example output:** See [`data/samples/example_mixed_scorecard.md`](data/samples/example_mixed_scorecard.md) for a full scored run against a realistic mixed-adherence scorecard. The scorer produces per-dimension observation, reasoning, verdict, and coaching-grade rationale — catching four distinct bias signals and a rating-to-evidence mismatch.

## What this is not

- **Not a hiring decision input.** SIIS scores the interviewer after the fact. Feeding this into candidate selection inverts the value proposition and creates exactly the kind of surveillance dynamic the framework is designed to avoid.
- **Not production-ready.** No database, no auth, no batch orchestration. It's a portfolio POC that demonstrates the core intellectual components: the scoring prompt, structured-output evaluation, and a working UI.
- **Not trained on real interview data.** All transcripts and scorecards in this repo are synthetic, generated by Claude against a meta-prompt designed to sample across the adherence spectrum.

## The ten dimensions

| Dimension | What it checks | Scored from |
|---|---|---|
| Standardized questions | Did the interviewer use a predefined question set? | Transcript |
| Behavioral evidence | Is feedback grounded in specific past actions? | Transcript + scorecard |
| Job relevance | Are comments tied to defined competencies? | Transcript + scorecard |
| Rating-to-evidence alignment | Does the score match the written justification? | Scorecard |
| Bias signal avoidance | No comparative language, personality adjectives, rapport cues? | Transcript + scorecard |
| Scoring discipline | Per-competency rubric applied, not a lone holistic verdict? | Scorecard |
| Follow-up probe quality | Did the interviewer probe on vague answers? | Transcript |
| Question form integrity | No leading or hypothetical questions? | Transcript |
| Competency coverage | Were all assigned competencies assessed? | Interview guide |
| Evaluation independence | Scorecard submitted before panel debrief? | ATS timestamps |

The first eight are scored by the LLM from text. The last two require external metadata (the interview guide and ATS timestamp data), so they're joined in at the `ScoringResult` layer rather than inferred by the model. This is a deliberate honesty: the model scores what it can score, and the framework doesn't pretend otherwise.

## How the scoring works

Four design choices are worth naming explicitly, because they're what separates a working scorer from a vibes-based LLM app.

**Tool use for structured output.** The scoring call uses Anthropic's tool-use pattern with `tool_choice` forced to the scoring tool. The model cannot return free-form text — it can only call `submit_siis_scoring` with a schema-validated array of eight verdicts. More reliable than JSON-mode prompting and it's what a production system would use.

**Forced observe → reason → verdict ordering.** The pydantic schema for each dimension puts `observation` first, then `reasoning`, then `verdict`, then `rationale`. Autoregressive models generate fields in order, so the verdict is conditioned on the preceding observation and reasoning rather than decided first and rationalized after. This is load-bearing, not cosmetic.

**Calibration examples per dimension.** Every dimension ships with a pass example and a fail example in the system prompt. This anchors the model's threshold and materially reduces drift on ambiguous cases. Without these, the model drifts toward over-passing polished-sounding interviews.

**No candidate outcome passed to the model.** The model never sees whether the candidate was hired, or their performance rating, or anything about them. SIIS scores the interviewer, not the interviewee. If the model knew the outcome it could reason backward from "this hire worked out" to "the interview must have been well-run," which is exactly the inverse of the causal claim SIIS is making.

## Generating synthetic data

```bash
# Preview what would be generated without hitting the API
python scripts/build_dataset.py --n 10 --dry-run

# Generate 30 interviews across strong/mixed/weak archetypes
python scripts/build_dataset.py --n 30 --out data/synthetic.jsonl
```

Each generated interview carries its ground-truth label set from the
spec. This is what the eval harness uses to compute the scorer's
per-dimension accuracy, precision/recall, and Cohen's kappa.

The sampler builds from three interviewer archetypes (strong, mixed,
weak) with dimension-specific pass probabilities for each. This is
more realistic than uniform random sampling — real hiring data has
correlated patterns (an interviewer who asks leading questions also
tends to write impression-based scorecards), and archetype-based
sampling preserves that structure.

## Running it

```bash
git clone https://github.com/YOUR_USERNAME/siis-poc.git
cd siis-poc

python -m venv .venv && source .venv/bin/activate
pip install -e .

cp .env.example .env
# edit .env and add your ANTHROPIC_API_KEY

python -c "from siis import score_interview_dry_run; \
  print(score_interview_dry_run(interview_id='x', interviewer_id='y', \
    role='Senior Software Engineer', \
    scorecard='She seemed sharp, great culture fit. Hire.')['user_message'])"
```

Dry-run doesn't hit the API and doesn't need a key. Good for poking at the prompt.

## Limitations and honest notes

**Synthetic data, not real interviews.** Every transcript and scorecard in this repo was generated by Claude against a meta-prompt designed to vary deliberately across the ten dimensions. This means the model is partly being evaluated on data from its own distribution. Real interviews look messier. A production deployment would need to re-calibrate against actual transcripts from the organization using it.

**The LLM itself could encode bias.** If the model has learned that certain linguistic patterns read as "professional" or "structured," SIIS could systematically over-credit interviewers who write in those patterns and under-credit equally-effective interviewers who don't. Auditing for this bias would be essential before any real use.

**No production-scale concerns addressed.** Cost per interview, latency, rate limiting, prompt injection from adversarial transcripts, data retention, works council and GDPR considerations for employee monitoring data — all deferred. The article this is based on is explicit that governance is the hard problem; this POC focuses on the technical piece.

**The eval harness is the next step.** Without inter-rater reliability numbers against a hand-labeled set, we can't make any claim about how well the scorer actually works. That's the next piece of work in this repo.
